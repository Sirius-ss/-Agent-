# 多业务场景 Agent 最小整改实施计划

版本 v0.1，独立评审稿。依据已确认的能力审计。实施范围为 implementation/。原始电商小二目录仅供对照。本轮交付限于计划，下面的验收项均为后续执行项。

## 整改边界

沿用现有聊天模型适配、JEV、LangChain Agent、Skill 加载、ToolExecutor、Redis/WebSocket 和三个服务。保留 DEMO 数据、数据库迁移、人工工作台和工单确认接口。此次整合的两个替换点是家电请求绕过共享 Agent 的分支，以及用户端分别维护两套聊天状态的做法。

| 阶段 | 任务与依赖 | 完成条件 | 单人估时 |
| --- | --- | --- | --- |
| A0 固定回归基线 | 先记录普通商城四类请求的分类、工具、业务结果，记录家电确认建单、转人工和历史恢复的现有结果。复用测试库和 DEMO 账号 | 保存脱敏输入、期望结果和运行环境。标出既有失败，作为 A、B 的对照 | 1 小时 |
| A1 接通路由和 Skill | 依赖 A0。将家电入口接回共享 Agent；增加场景允许的任务、Skill 描述及渐进披露规则 | 显式入口不会误入电商。普通聊天能识别家电意图。伪造场景或加载越权 Skill 的请求被拒绝 | 2 小时 |
| A2 接通工具和输出校验 | 依赖 A1。复用家电领域函数，注册工具，接回统一执行记录，输出结构化卡片并核验证据 | 一条真实家电请求留下模型 tool call、执行结果和最终校验记录；无证据、跨型号、越权设备均不能生成肯定诊断。运行 A 阶段回归 | 4 小时 |
| B 统一用户聊天工作台 | 依赖 A2 的卡片契约。提取原聊天工作台，将已有家电交互作为卡片嵌入，保留快捷入口和工单切换 | 两个入口使用同一消息列表、输入框、历史和实时连接生命周期。切单、刷新、断线恢复正常，重复事件只展示一次。运行用户端构建及交互验证 | 4 小时 |
| C 跨服务回归与修复 | 依赖 A、B。用相同数据回放 A0；补真实模型、双用户权限、并发确认、双端实时与交接验证 | 按下面矩阵记录通过、失败、受阻及复现方法；关键项全部通过后申请切换 | 3–5 小时 |

合计约 14–16 个有效工时。建议第一天做 A0–A2 并固定卡片契约，第二天完成 B、C。估算以现有服务、测试库和模型凭据可用为前提。若两天合计仅有 12 小时，优先取消视觉调整、复用原卡片布局，以人工浏览器回归替代新增浏览器自动化。仍不足时交付已验证阶段，单列未验收项，保留原入口。

## A 阶段的关键实现决定

1. **场景归会话服务管理。** service_scene 是持久化的会话领域。显式家电入口通过既有鉴权创建流程建立家电会话，Worker 从数据库读取场景、用户和 context_version 传给 AI。skill_code 是本次运行的任务。显式家电场景加载 APPLIANCE_SERVICE Skill，由受控的设备选择、诊断、保修、预览等任务规则逐步开放工具。首版一个家电 Skill 足够，无需每种卡片建一个 Skill。
2. **普通聊天保留 JEV。** 对普通入口沿用 JEV 分类，增加家电售后候选意图。普通订单发货、物流、退货等沿用电商 Skill。明确咨询设备故障或维修时，回复带“进入家电售后”按钮；点击后由会话服务建立或恢复本人家电会话，携带原问题并只提交一次。意图含混时先澄清。JEV 分类结果和模型输出都没有修改现有会话领域的权限。
3. **模型负责选择工具，服务端控制权限。** 初始只披露场景内 Skill 摘要及加载入口。加载家电 Skill 后，按服务端已验证状态披露本人设备查询、型号知识检索、保修查询、维修预览准备等工具。显式设备选择由后端核属，执行时再次检查用户、场景、已加载 Skill、设备和允许操作。模型参数不能覆盖身份和已验证型号。工具调用走现有 ToolExecutor，关联运行、工具调用、实际结果、错误和耗时。用于识别意图的伪工具不能充当业务工具调用证明。
4. **沿用确定性控制。** 型号约束、故障码匹配、保修计算、单步推进、冒烟停查与转人工继续由现有业务逻辑控制。conversations.service_context 与 context_version 决定当前步骤；Worker 写入时拒绝过期结果。AgentOutput 对普通聊天保持兼容，对家电附加类型明确的卡片数据。Validator 对照本轮真实工具结果验证设备、型号、片段来源和建议步骤，包括只有知识引用的回答。无匹配时显示缺少依据，工具失败显示可重试结果。
5. **确认建单与工具权限分开。** 维修预览准备工具只返回可供用户打开预览的业务信息。工作台调用已有后端接口取得与用户、设备绑定的具体预览，展示保修提示。仅用户点击该预览的确认按钮后，才调用既有确认接口。模型工具目录不包含确认建单能力。沿用后端预览替换事务、幂等和设备级待受理工单唯一约束。

## B 阶段的复用边界

从 App.vue 提取现有聊天列表、输入、历史和滚动行为为 ChatWorkspace。保留商城及个人页面。/chat 和 /appliance 指向同一工作台，由入口选择或恢复相应会话；切换工单时绑定对应的已授权会话。按会话 ID 归集消息，按消息 ID 去重，切换时防止迟到的历史响应覆盖新会话。历史响应与实时事件使用同一卡片渲染器。复用当前用户连接，页面切换时清理订阅。

从 ApplianceService.vue 迁出设备选择、单步诊断、说明书引用、保修、维修预览/确认和工单查询交互。卡片只接收数据并上报操作。已失效预览、历史步骤及已确认工单按当前业务状态禁用旧按钮。切换完成后移除独立聊天逻辑。

## 风险和降级

- **JEV 或聊天供应方不可达。** 检查已配置代理和连通性，离线验证契约；普通聊天保留现有失败处理，显式家电入口仍可进入正确领域。真实模型链路标记待验证，不能用关键词路由替代验收。
- **旧会话缺卡片或已有进行中的预览。** 保留文本回放，进入会话时从权威业务状态恢复当前设备与预览。若有歧义，重新打开预览并让用户确认。
- **路由误判或工作台回归。** 先用显式入口验证新链路，再启用普通聊天引导。按阶段保留可单独回退的改动；UI 验证失败时延迟统一入口切换。权限、证据、确认、幂等、冒烟转人工任一失败均阻止发布。

## v0.2 独立评审补充

1. **状态词汇。** `service_scene` 复用 Conversations 的持久化领域。现有 JEV 的 `check_input` 输出候选 SkillCode 或空，没有独立 intent_code 列；候选意图只作本轮路由输入。SkillCode 是 SkillCatalog 的键；运行时 `skill_code` 仅表示当前授权加载的 Skill。普通电商保留现有受控预加载；家电通过受限 load_skill 写入 LangChain Command，SkillScopeMiddleWare 按已加载 Skill 裁剪工具。加载和执行均校验可信场景。家电的 `workflow_stage` 属于 service_context JSON，优先从 device、pending_step、steps 和结束结果推导，不能区分的终态才补 JSON 标记。context_version 复用会话版本列，状态有效变化时递增。这五个概念无需五个数据库字段。
2. **诊断推进。** 沿用 POST /api/v1/chat/messages 的 type=step_feedback，提交 conversation_id、稳定的 message_id，以及 content 中的 device_id、step_id、outcome（resolved/unresolved）和展示卡片时的 context_version。customer-service 是诊断状态唯一写入方。事务内按登录用户锁定会话，检查 AI 模式、家电场景、当前核属设备、待答步骤及版本；同一操作重放返回原结果，过期卡返回冲突并刷新。记录操作和结果，已恢复结束自查，未恢复按已核验的同型号片段步序推进一步，耗尽后进入维修预览准备。所需步骤由 ai-service 从已引用片段提供，不能由模型编造。状态、消息及待处理轮次原子提交。Worker 每轮读取最新 service_context、版本与消息快照；AI 返回的展示或证据只能按原版本应用，不能再次消费该反馈。冒烟或人工接管优先使旧卡失效。
3. **电商转家电幂等。** 以登录用户和原电商消息 ID 为稳定键。后端核实源消息、会话归属及对应引导，读取已有原文；前端只传来源标识。使用事务锁串行化同一键，以有命名空间的确定性 ID 写入目标用户消息，复用 messages.message_id 的唯一约束。先按此 ID 查原目标：命中即返回其 conversation_id 和消息 ID（包括已关闭的目标），否则在同一事务内创建或恢复家电会话、写入原问题并登记一次待处理轮次。提交后通知 Worker，按既有轮次恢复机制处理通知失败。禁止先提交建会话再用第二次 HTTP 请求发问题。并发两次、响应丢失重试及跨账号伪造来源均列入验收。

v0.2 授权先建立 A0，后续阶段以各自验收结果为准。
